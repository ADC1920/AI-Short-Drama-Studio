# 原著改编：结构提取与职责切分

> 用途：把长篇小说变成可排产的结构（章节索引、情节点位置、分集区间），并守住与 `onlyshot-drama` 的职责边界。
> 本文件管「怎么提取」，不管「写什么」——选题、爽点、钩子、人设弧光都是创作判断，属 `onlyshot-drama`。

## 一、职责切分（两个技能不打架的唯一保证）

| 问题 | 归属 | 本技能做什么 |
|---|---|---|
| 这个题材该不该做、目标受众是谁 | `onlyshot-drama` | 不碰 |
| 这章有哪些情节点、在哪一行 | 本技能 `novel_index.py` | 机械抽取，带原文位置 |
| 哪几章适合做一集 | 本技能 `candidates` 只给字数区间 | 不定钩子、不排节奏 |
| 这集的爽点/反转怎么设计 | `onlyshot-drama` | 不碰 |
| 这一集怎么落到分镜与出片 | 本技能五工位 | 工作室流程 |

代码层面的约束：`novel_index.py` 的 `CREATIVE_WORDS` 黑名单会检查 `candidates` 的输出，出现「钩子/爽点/反转/卖点/爆点/题材/受众」等创作词即报 `AssertionError`。这条断言写在 selftest 里，将来有人往 `candidates` 里加创作建议会当场失败。

这不是过度防御——两个技能职责一旦模糊，用户就会在错误的技能里问问题，两边都答一半。

## 二、能做什么

### 2.1 建索引

```bash
python scripts/novel_index.py index 原著.txt
# 产出 原著所在目录/_novel/index.json
```

索引内容：

- 编码识别（UTF-8 / GBK 自动，两种都能建）
- 章节切分：识别「第X章 / 第X回 / 第X节 / Chapter N / N.」五种形态
- 每章的字数与字符起止偏移
- 情节点候选：按段落切分，每段取首句作 `quote`，带 `offset` 可回查原文
- `read_range` 与 `unread`：记清分析了哪几章、剩哪些

### 2.2 分集区间建议

```bash
python scripts/novel_index.py candidates <项目> --episodes 24
```

按字数把章节均分成 N 段，给出「第 1-3 章 → 第 1 集」这样的区间。**只给区间，不给任何剧情判断。**

### 2.3 分批处理大文件

正文超过 200KB 时，`index` 只出章节骨架，情节点留空并提示分批：

```bash
python scripts/novel_index.py index 原著.txt --chapters 1-5 --out _novel/part1.json
```

这是「长剧本分批读时记录实际已读范围」纪律的工程化——`read_range` 字段就是记录，`unread` 是待补清单。

## 三、不能做什么（容易误用的三处）

### 3.1 不要把情节点候选当改编方案

`points` 是按段落机械切出来的，一段一条，不代表这段有戏剧价值。它只是「这里有个可引用的位置」，供后续核对原文。真正选哪些点做戏，是创作判断。

### 3.2 不要用 `candidates` 的区间直接排产

它按字数均分，不考虑剧情完整性。一个自然的集末（比如主角身份揭露）可能落在区间中间。`candidates` 给的是起点，不是答案——具体在哪一章断集，要看剧情。

### 3.3 不要在索引里写剧情摘要

索引是结构化提取的结果，不是二次创作。写摘要会引入主观判断，也会让 `quote` 与原文对不上。要摘要用 `onlyshot-drama` 或直接让 agent 读原文。

## 四、与其他工位的衔接

```text
原著.txt
   ↓ novel_index.py index
_novel/index.json（章节 + 情节点位置）
   ↓ candidates 给区间建议（人确认边界）
第1集/剧本.md …（剧本台）
   ↓ 五工位推进
成片
```

`studio.py init --novel 原著.txt` 在初始化时顺带建索引。`studio.py status` 会在有索引但某章未分析时提示。

## 五、验收要点

| 检查 | 通过标准 |
|---|---|
| 章节切分 | 章节数等于人工数；各章字数合计等于全文 |
| 偏移连续 | 前一章 end 等于后一章 start，无重叠无空隙 |
| 情节点可回查 | 任取一个 point，用 `start + offset` 定位原文，取出的字符串逐字等于 `quote` |
| 编码兼容 | 同内容 GBK 与 UTF-8 两份，章节数与字数一致 |
| 边界守住 | `candidates` 输出无创作词 |

前四条 `novel_index.py --selftest` 已覆盖；第五条是断言，改代码时若破坏会立刻失败。

## 六、一个真实的判断边界

小说改编最难的部分不是提取，是**判断哪几章能撑起一集、哪里的情绪能形成钩子**。这部分无法机械化，也不该伪装成可机械化。本脚本刻意止步于此：它把「原文在哪」这个事实问题解决掉，把「该怎么改」留给创作层。

如果把两者混在一个脚本里，会出现两种坏结果：要么脚本给出看似精确其实瞎猜的分集建议，要么创作判断被压在结构化输出里没人看。分开是更好的选择。
